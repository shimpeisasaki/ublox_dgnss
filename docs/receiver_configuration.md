# GNSS受信機の採用設定と残課題

文書整理日：2026-11-16。2026-11-10の保存済み作業記録と現行ソースを整理した資料。
今回、新たな受信機接続・値の読み戻し・設定書き込み・ネットワーク接続は行っていない。

## 役割と現在の方式

受信機が衛星選別と測位を行い、ublox_dgnssが位置・速度・共分散・有効状態をROSへ変換する。
独自の測位再計算・平滑化・他センサー融合は追加していない。
利用側は出力の欠落・鮮度・品質と他センサーの状態から採用可否を判断する。
cat_robotの起動はGNSS無効が既定で、単独測位とRTKを選択できる。
GNSSのNav2への融合は、その起動設定には含まれない。

起動引数は [README](../README.md#gnss_launch-compatible-topics)、
有効な同一iTOWだけを配信する条件は [出力契約](gnss_output_contract.md)、
RTKの既定CIT局・任意の松戸局・認証管理は [RTK資料](rtk_tsudanuma.md)を正本とする。

## launchと保存設定の境界

現行 `ublox_dgnss/launch/gnss_launch_compatible.launch.py` は5 HzとUSB protocol/outputを
明示し、通常の補正入力を無効にする。RTK launchでのみ補正入力を有効にする。
起動時の指定はRAMへの適用であり、BBR・Flashへは書き込まない。
衛星系・最低衛星数・仰角・C/N₀は受信機の保存設定を管理元とし、このlaunchは上書きしない。
F9P TOMLは対応キーの一覧であり、受信機全体を既定値へ戻す設定ファイルではない。

## PyGPSClientを使う際の注意

当時の環境はPyGPSClient 1.8.0 / pyubx2 1.4.1。
専用venvは `~/.local/share/pygpsclient/venv`、ランチャーは `~/.local/bin/pygpsclient`。
これは過去の導入記録であり、別PCに同じ環境があるとは限らない。
通常運用の測位エンジンではなく、設定送信と読み戻し確認に用いた。

[当時のレビュー](history/2026-11-09_pygpsclient-config-review.md)では、異なるコマンドのACK、
対象キーを含まないGET応答、SET層の未選択、符号付き整数の上限に関する問題を疑似応答で再現した。
成功アイコンだけで設定反映を判断せず、同じキー・層を読み戻し、期待値と照合する。
Flashだけへの保存を現在のRAMへの適用と混同しない。
レビュー時の候補値（1 Hz・6衛星・15°・FIXMODE=2）は現行の採用値ではない。
このレビューを最新版全体の評価や、指摘の修正済み証明として扱わない。

## できていることと次の確認

出力のiTOW一致・有効性・鮮度・無効時非配信は実装済み。
旧HANDOFFにある「launchは4 Hz」「1 Hzへ変更する」「出力整合性が未修正」は過去の状態である。
RTKはCITが既定になっており、松戸局のみ・RTK自体が未対応という古い説明も現行仕様ではない。
過去のビルド・疑似ROS試験・ループバックNTRIP試験は
[履歴](history/2026-11-10_gnss-handoff.md)と各正本の記録を参照し、今回の再実行成功と混同しない。

残っている検証は次のとおり。実行には対象操作の明示指示が必要。

1. 電源再投入・再起動後のRAMと保存設定の保持確認。
2. 実機ROS出力の正常出力率、通信断・復帰、時刻・鮮度の確認。
3. RTCMの受信機への転送、RTK Float/Fixの有無・継続性、位置精度の確認。
4. 開けた場所と建物付近で、誤差・共分散・使用衛星数・欠測を比較する評価。
5. PDOP・位置精度マスク、3D限定、閾値を変える場合の採用判断と記録。

NTRIP受信の成功はRTK Fixの証明ではない。高仰角・強いC/N₀・小さい共分散も実位置の
正しさを保証しない。マルチパス指標を条件に受信機内部で自動除外できるとは未確認であり、
その機能があると断定しない。
